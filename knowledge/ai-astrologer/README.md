# ASTRO SIVAM source-based astrologer — knowledge base

This directory contains local data used by the customer chat. The current reply path is deterministic PHP logic; it does **not** call an AI/chat agent or an external model and does not need an API key.

```text
knowledge/ai-astrologer/
├── README.md
├── DEPLOYMENT.md

├── sources.json

│   └── guardrails.json
```

The customer reply implementation is in `api/astrology/ai_astrologer_offline.php`; shared retrieval, chart/rule helpers, source filtering, and safety checks are in `api/astrology/ai_astrologer_provider.php`. The endpoint is `api/ai_astrologer.php`.

## Source-registry limits

The registry currently contains **224 catalogue records** and **13 excluded records**. Its verification levels are:

| Registry status | Count | What the label means |
| --- | ---: | --- |
| `content-read` | 11 | The text was opened/read and can support content-level claims within its verified scope. |
| `metadata-verified` | 144 | Bibliographic details were checked; this does not verify specific teachings or verses. |
| `linked-not-opened` | 67 | A link was recorded but the linked text was not opened; it is not evidence for a claim. |
| `catalogue-verified` | 1 | Catalogue-level record only. |
| `dead` | 1 | Link/source is unavailable and must not be used. |

These are catalogue entries, not 224 searchable full-text books. The project does not scrape or index the full text behind catalogue links. Replies rely on the reviewed rule/remedy text and any eligible chart/report facts, then cite only references allowed by the source's verification level. Never describe the entire registry as searchable book content.

See `SOURCES.md` for the source table and `VERIFICATION_LOG.md` for verification details and failed links.

## Reply data flow

1. The authenticated PHP endpoint enforces customer/report access and request limits.
2. Where a session is attached to an eligible report, PHP rebuilds chart facts from that customer's saved order inputs. It does not trust a client-submitted chart.
3. Local matching checks fixed safety/refusal routes, question topics, curated conditions, chart/report readings, and remedies.
4. The answer builder renders a reply in English, Tamil, or Hindi, applies the local safety guard (including the health/doctor rule), and returns bubbles plus an eligible source line or human handoff.

Topic selection uses curated phrase/rule matching; it is not a general language model. An unsupported question should receive an honest limitation/handoff rather than an invented answer. Replies are not generated by searching the 224-entry catalogue.

## Rules and safeguards

- `rules/life-areas.json` contains the eight report areas and reviewed chart conditions, wording, practical steps, and source references.
- `rules/remedies.json` contains the limited remedies the chat may offer.
- `rules/guardrails.json` defines refusal routes, prediction limits, health wording, and safety language in all supported languages.
- `rules/guided-questions.json` is the customer-facing menu: life areas mirroring Birth Jathagam page 2, the three other service reports (Wedding Matching, Baby Naming, Subha Muhurtham), doshas, remedies, order help, and complaints. Customers tap an option id; free text is admin-testing only.

## The three service reports in the chat

`rules/guided-questions.json` carries a chapter for each non-Jathagam service:

| Chapter | Service | Answered from |
| --- | --- | --- |
| `wedding-match` | `MARRIAGE_COMPATIBILITY` | the report's 10-Porutham table: score, verdict, matched/unmatched poruthams and their explanations, Rajju/Vedha, Sevvai (Kuja) Dosha samyam and its remedy |
| `baby-naming` | `BABY_NAMING` | the report's birth star, pada, the four pada sounds, the name list for the birth-pada sound, and the provenance of the name recorded on the order |
| `muhurtham` | `MUHURTHAM` | the report's own calendar: recommended dates, the strongest date and its Nalla Neram window, why a date is auspicious, the Rahu Kalam windows to avoid, and the place the dates were calculated for |

Two rules keep these honest:

1. **A chapter is shown only for a report the account already holds** (`astro_ai_entitled_service_types()`), and the same check runs again in `ask()`. The server decides; the client only renders what it is sent.
2. **The chat reads the report, it never re-judges it.** `astro_ai_service_facts()` copies the engine's own values out of the order's rebuilt result; a question about a report that is not attached to the conversation is answered with a request to attach it, never with an invented number.

The customer attaches a report with the `bind` action (`ai_astrologer.bind(sessionId, orderNumber)`), which re-checks ownership and delivery in SQL before the conversation reads from it.
- Suppressed and excluded references cannot be shown to customers. Citation level must not exceed the registry's verification level; a book-level bibliographic record does not justify a chapter/verse claim.
- Health replies must not diagnose or prescribe and must direct the customer to a qualified doctor.

The automated contracts are in `tests/ai-astrologer-knowledge.test.ts`, `tests/ai-astrologer-sources.test.ts`, `tests/ai-astrologer-tamil-only.test.ts`, and the PHP-WASM reply-path tests.

## Deployment and diagnosis

Deploy the whole `knowledge/` directory beside `api/` in the document root. `deploy_cpanel.sh` includes it. PHP `mbstring` is required for Tamil/Hindi text handling.

An administrator can run the local-only check from **Admin Portal → Setup → Check Source-Based Astrologer** or `/api/ai_astrologer.php?action=diagnose`. The check never pings a provider or makes an outbound network request. Full deployment instructions are in `DEPLOYMENT.md`; diagnosis notes are in `../../AI_CHAT_NOT_REPLYING_FIX.md`.
